# 卡牌DIY + 自定义规则对战游戏

产品方案 · 项目管理文档

> 本文档定位：**给老板/PM/开发团队**的阶段规划与阶段1定稿规格。
> 状态：阶段1 已由老板确认，定稿。后续阶段为规划蓝图，待逐阶段开启。

## 0. 产品一句话

一款让玩家**用可视化节点图自制卡牌与规则、并能对战**的卡牌游戏，定位 **创作者 / UGC 向**。

***

## 1. 核心需求（老板已逐项确认）

| 维度       | 决策                                        |
| -------- | ----------------------------------------- |
| 平台       | 先 PC，后移动                                  |
| 卡牌自定义    | 节点图（方案 A：首批 14 个官方节点）                     |
| 规则自定义    | 先白名单配置项，不改引擎；后期逐步开放                       |
| DIY 使用边界 | **只进私房**，天梯永远官方牌池                         |
| DIY 可信度  | **信任本地文件**（客户端直接用，不重建校验）                  |
| 审核工作流    | 系统建议 + 人工批准（仅服务社区展示）                      |
| 对战模式     | 私房（优先）→ 官方天梯 → 赛事/观战（靠后）                  |
| 内容分发     | DIY 存**本地文件**（.diycard / .diyrule），可导出/导入 |
| 开发节奏     | 阶段1 = 编辑器 Demo 验证                         |

### 关键约束（避免天坑）

* 不搞"完全开放引擎"：规则 = 官方白名单配置，引擎逻辑仅官方层开放（插件化规则集）。

* DIY 只进私房 + 信任本地文件 → 规避了 UGC 天梯平衡 / 服务器权威重建 / 大规模审核三大重负担。

## 3. 阶段1 Demo — 定稿规格（老板已确认）

### 3.1 目标（一句话）

> **验证"玩家用节点图做一张卡 → 能在本地人 vs AI 对局里真正打出来"这个核心闭环。**

### 3.2 范围边界（严禁超出）

| 做                           | 不做               |
| --------------------------- | ---------------- |
| 节点图编辑器（拖/连/存）               | 注册登录、账号存盘        |
| .diycard 导出/导入              | 社区上传、审核          |
| 人 vs AI 单机对局（沿用 Offline 模式） | 双人同机（已砍）、私房联机、天梯 |
| 把 DIY 图解释执行                 | 移动端、赛事、观战        |

### 3.3 功能清单（最小可用集 MVP）

1. **编辑器**

   * 左侧节点面板：14 个节点，按 4 类分组

   * 画布：拖入节点、连线（执行流=实线 / 数据流=虚线）、删除

   * 节点输入框：填固定值 或 拖连线取值（复用已改造的 ValueSource 体系）

   * 右侧实时预览卡面（费用/攻血/效果文字）
2. **卡牌数据**：输出 .diycard JSON（schema 1.0，meta + graph）
3. **对局**：固定官方规则（30血 / 法力0-12每回合+1 / 起手5张每回合抽1 / 手牌上限15）+ 人 vs AI（AIPlayer，先随机后深度）+ 出牌/攻击 + 解释器跑自制效果
4. **解释器**：NodeGraphRunner，拓扑排序执行，桥接现有 EffectData（已支持 amount）

### 3.4 节点图数据格式（核心规约）

```
.diycard = { schema, meta{id,author,title,cost,attack,hp,type}, graph }
graph   = { nodes[], connections[] }
node    = { id, defineId, posX, posY, inputs{}}     ✓ 对齐 Classic.ddcp
connect = { sourceNodeId, sourcePort, destNodeId, destPort }  实线=exec / 虚线=data
```

* 端口两类：**执行流**(exec/enter) 与 **数据流**(数值/卡牌)

* 运行时 NodeGraphRunner 按 connections 拓扑排序，逐个节点 → 查 NodeDef 字典 → Handler → 内部复用现有 EffectData

### 3.5 最小节点清单（方案 A，14 个）

* 入口/目标：100001 效果入口、100002 取目标

* 动作：100010 造成伤害、100011 治疗、100012 抽牌、100013 加Buff、100014 召唤、100015 弃牌、100016 加法力

* 数据/运算：100020 取攻击力、100021 取血量、100022 取法力、100030 四则运算(Add/Sub/Mul/Div/Mod)

* 流程：100040 条件判断、100041 循环N次、100042 求和（预留）

> 足以组合出「战术洞察」：目标每1攻抽1张。（入口→取攻击力→四则运算→抽牌）

### 3.6 验收标准（Demo 完成定义）

1. 编辑器能拖 5 节点连出「战术洞察」效果图
2. 保存导出 .diycard，重新导入无损坏
3. 人 vs AI 对局出这张卡，效果正确生效（目标5攻 → 抽5张）
4. AI 正常对战、会打出/施放自制卡；普通官方卡不受影响

### 3.7 暂存默认项（无强度校验 / 预置官方卡 / 中文界面）

* ① 预置一批官方卡（便于组牌对战）

* ② DIY 暂不做强度校验（信任本地文件），正式版再加白名单

* ③ 编辑器界面用中文

## 7. 阶段2 — 「规则开放 + 私房」细化规格

### 7.0 阶段2 目标（一句话）

> **让 UGC 玩家能把自制卡带入玩家对战**：规则可做白名单调整、可发布自定义房间，自制内容有作者归属。为阶段3 社区/天梯打底。

### 7.1 范围边界

| 做                        | 不做               |
| ------------------------ | ---------------- |
| 规则白名单配置（改官方白名单项）         | 完全开放引擎（引擎逻辑官方独占） |
| 私房对战（好友/房号开局，DIY 可用）     | 天梯（官方牌池，留阶段3）    |
| 极简账号（登录/昵称/本地身份）         | 完整社交、好友列表、短信号    |
| DIY 作品作者归属 + 作品列表（本地）    | 社区上传、排行榜         |
| .diycard / .diyrule 导出导入 | 赛事、观战、移动端        |

### 7.2 模块 A：规则白名单（自定义规则的落点）

* 新增 `RuleData` 资源 + `.diyrule` 文件，内容为官方白名单键值对

* 守卫：规则键必须命中白名单，值必须在允许范围（例如 `starting_hp` 只能 20\~40 整数）

* 对战应用：私房创建时选择一套 `.diyrule`，Host 下发给 Sync；房间内所有玩家采用同一套规则

* 白名单首批（草案）

  * 数值类：`starting_hp` / `mana_per_turn` / `mana_max` / `cards_start` / `cards_per_turn` / `cards_max` / `deck_size` / `dup_max`

  * 开关类：`mulligan`（有无换牌）/ `second_bonus`（后手补偿）

  * <br />

    > 机制类（胜负规则/回合流程）**不开放**，留后续扩展；避免"完全开放引擎"天坑。

### 7.3 模块 B：私房对战

* 场景：创建房间（选规则 → 生成房号/share code）→ 好友输入房号加入 → Host 开始

* 技术：沿用现有网络（Netcode Host + Client），把"房间配置（规则 + 双方 DIY 牌组）"作为同步协议

* DIY 数据流：**私房内双方各自本地持有 .diycard**，仅同步"卡牌 ID + 校验签名"，不每次全传图（省流量 & 快）

* 校验：双方比对规则的 hash 一致才开（防规则不一致）

* Server：DIY 在私房信任本地文件（不重建校验），与天梯隔离

### 7.4 模块 C：极简账号

* 目的：让"作者身份 + 作品归属"可寻址，为阶段3 存盘/社区铺路

* 方案：极简账号 = 本地 `account_id + 昵称 + 签名`；先不强制联网注册（本地生成）

* 作品归属：每个 .diycard 写入 `author`（account\_id + 昵称），导出/导入保留

* 阶段3 再升级为真实服务器账号与云存盘

### 7.5 节点/能力扩展（阶段2 可选）

* 节点从 14 → 约 20 个（新增：取随从数、取手牌数、条件分支更多比较符）

* 规则相关：新增"读规则值"节点（如读 `starting_hp` 做卡牌判定）——联动模块 A

### 7.6 验收标准（阶段2 完成定义）

1. 能建一个使用 `.diyrule`（改血量/法力）的私房，两个客户端加入并开战
2. 私房内双方都能用各自的 DIY 卡，效果正确生效
3. 规则 hash 不一致的两个客户端，拒绝开战并给提示
4. .diycard 导出/导入保留作者信息；昵称可改
5. 官方默认规则对局不受影响

### 7.7 技术落点（阶段2）

| 模块                | 落点                                            |
| ----------------- | --------------------------------------------- |
| RuleData｜.diyrule | 新增 纯数据类 + 资源 + JSON 序列化；复用 GameplayData 的取值逻辑 |
| 私房                | 复用 Netcode；新增 RoomConfig 同步协议（规则+玩家DIY签名）     |
| 账号                | 新增 AccountData 纯数据（本地 account\_id/昵称/签名）      |
| 作品归属              | .diycard meta.author 写入 account 信息            |
| 读规则值节点            | 新增 ValueRuleStat（ValueSource 子类）              |
